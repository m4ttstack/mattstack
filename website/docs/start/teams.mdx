# Teams and invites

An org is one git repo that rt manages, shared by everyone in it: settings, secrets, skill packs, and forge access, distributed to every member's Mac. Inside the org are teams. Each team is a folder with its own settings and its own skill pack, and the org's settings apply to every team.

The org's data lives on its own branch of that repo, the data branch, named `mattstack` unless the org picked another. The repo's `main` holds only a small pointer to it, so `main` stays free for anything else.

A Mac holds one org. Its clone lives at `~/.mattstack/orgs/<org>/`, a folder named for the org:

- `mattstack/org/` holds the org's settings, its secrets and its base packs.
- `mattstack/teams/<team>/` holds one team's settings and its pack, the team's Claude plugin, under `plugin/`.

Each Mac holds only the team folders its role reaches. An org owner's or admin's Mac holds every team. Everyone else holds the org's own files and the teams they are on or own. When you leave a team while your copy has changes in its folder, the folder stays, and the **Team folders** row in setup status says what to do.

## Roles

The org's `mattstack.org` setting names who may change what:

- An **org owner** can do everything an admin can, and is the only one who renames the org or changes who the org owners are. `owners` lists them; when it lists nobody, the admins are the org owners.
- An **admin** changes anything else in the org: its settings, every team folder, the roster, secrets and invites.
- A team's **owner** changes that team's folder: its settings and its pack. They can also put people already in the org on their own teams, or take them off, but cannot change anything else about them.
- A **member** changes nothing shared. Their Mac only pulls the org.

A change you are not allowed to make is refused before anything is written, with a note naming who to ask: the team's owners, then the org's admins.

:::note
An app older than v2.25.0 reads only `admins`. Until every member has updated, list a new org owner in `admins` too.
:::

## Creating an org

In setup's team step, choose **Create a team**, give it a name, and leave **Others will join later** on if teammates will follow. For the repo, paste the URL of an empty repo on GitHub, GitLab, or anything git can push to. When the `gh` CLI is signed in, you can instead let mattstack create a private GitHub repo under an owner you pick. Setup scaffolds the org under `~/.mattstack/orgs/<name>/`, and its Install step pushes it.

The org starts with one team inside. That first team takes the org's name, unless you name it with `--first-team`. You become the org's owner and the first team's owner. The org starts with its data on the `mattstack` branch and a pointer on `main`.

From a terminal:

```bash
rt team create Acme --first-team widgets --remote git@github.com:acme/mattstack-team-acme.git   # or --create-repo <owner>
rt team publish                                                                                  # push your org changes
```

`--others` is the terminal form of **Others will join later**.

## Adding a team

An admin adds a team with its owners, then puts people on it:

```bash
rt team add gadgets --owner dev2
rt team members set dev3 --teams gadgets
```

`rt team add` writes the team's folder and pack and shares them with the org.

A team's owner puts someone who is already in the org on one of their teams, or takes them off it:

```bash
rt team members add dev3 --to gadgets
rt team members drop dev3 --from gadgets
```

## Team directory

The team directory tells every mattstack app which Slack channels and Linear team belong to each team. It is one org setting, `mattstack.directory`, and only an org admin can change it.

List every team the apps should know about, including teams that do not use mattstack. A name that matches one of your org's teams is that team; any other name is a team outside mattstack.

```json
{
  "teams": {
    "widgets": {
      "linear": { "team": "WID" },
      "slack": {
        "codeOwnersChannel": "pod-widgets",
        "channels": [{ "name": "widgets-review", "kind": "review" }]
      }
    },
    "gadgets": {
      "slack": { "codeOwnersChannel": "pod-gadgets" }
    }
  }
}
```

| Field | What it means |
| --- | --- |
| `teams.<name>` | One entry per team. |
| `linear.team` | The team's Linear team key. The board links tickets with this prefix, and setup reads it when connecting Linear. |
| `slack.codeOwnersChannel` | Where other teams ask this team for code owner review. The board matches a CODEOWNERS section to this team by it. |
| `slack.channels` | The team's other channels, each with a `name` and a `kind`. The board reads the `review` kind as the team's review channel. Teams can add kinds of their own. |

Channel names leave off the `#`; matching ignores case and a leading `#`, so `#Pod-Widgets` still matches `pod-widgets`. Two teams cannot share a code owners channel. `rt settings set` accepts a kind no app reads, with a notice; the console accepts it without one.

To change the directory, edit it in the console's settings page, where it opens in the JSON editor, or run:

```bash
rt settings set mattstack.directory '<json>' --scope org
```

### Moving to the team directory

The team directory changes the shape of the org's shared settings, so an org moves onto it as layout 3 of the org repo. An org admin converts the org once, from a mattstack checkout:

```bash
bun scripts/move-to-team-directory.ts ~/.mattstack/orgs/<org> --admin <username>
```

On its own it prints the plan and writes nothing. Run it again with `--write` to make the move. It fills in each team's entry from that team's older settings, never overwrites an entry that is already there, and deletes the old values:

- `board.slack.channel`.
- `mattstack.integrations.linear.teamKey`.
- a codeowners tab's `slackChannel`, when it equals the team's code owners channel.
- `board.ticketPrefixes`, when it holds only the team's Linear key.

It also marks the org as layout 3 and puts the whole move in one commit on the branch your clone has checked out. Review it with `git show`, then publish it with `rt team publish`. The script refuses while team sync is on for your Mac, because sync could publish the move before you review it; the refusal names the commands that turn sync off.

A member's app that reads only an older layout never pulls the converted org. Its daemon holds the clone at the last commit it can read, and the **Org layout** row in setup status says to update the app. After the update, the next pull brings the move in, and the member runs nothing. An app older than v2.21.1 does not hold: it pulls the move, and its board posts to its built-in `#code-review` channel instead of your team's. A board older than v2.21.0 also loses its tabs. Update every member's Mac to at least v2.21.1 before you publish the move.

## Inviting a member

Only an org owner or admin invites, and only while their clone is on the org's data branch. Open **Settings → Team** (or **Invite teammates…** on setup's last screen), pick the team when the org has more than one, type the teammate's GitHub or GitLab handle, and click **Invite…**. You get an invite link to copy or share, plus a paste block for chat clients that mangle links, with the invite's expiry and the forge access it grants. When rt can't grant forge access itself, the steps to do it by hand appear underneath.

The link looks like `https://mattstack.dev/join#<code>`. The code lives in the URL fragment, so it never reaches the join page's server.

From a terminal:

```bash
rt team invite --handle dev3 --teams widgets   # --teams takes a comma-separated list; your own team when left out
```

The same pane shows the org's name, your team, the remote, the last push, and your team's members.

## What a joiner sees

The joiner opens the invite link, or pastes the code into **Join a team** in setup's team step. A Mac holds one org: a join is refused while another org is set up on it, and joining your own org again is fine: **Settings → Team → Rejoin this org…** takes a new invite from your org admin. The checklist then runs a forge-auth preflight against the org repo:

- If the joiner's forge account (GitHub or GitLab) cannot see the repo, a warning names the problem and suggests asking for access. The `access.team-repo` checklist row holds Install until access is resolved.
- If access is confirmed, setup continues normally.

The join clones only the org's data branch, then narrows it to the folders the joiner's role reaches. Whatever else the org repo holds, like an app's code on `main`, stays on the remote and never lands on the joiner's Mac.

An invite minted before the org was renamed names the org by its old name. The join refuses it with "This invite names the org by an old name; ask for a fresh one" and removes the clone it just made; ask an admin for a new invite.

The invite also carries the joiner's board token. When this Mac's board ends up without one, the **Board peering** row says the board does not peer yet. It never holds up Install or Finish, but setup keeps listing it, and the setup check after an app update notifies you about it. The fix is on the admin's side: ask them to re-invite your board, with `rt team invite --handle <your forge username>` (then run `rt team join` with the new code). The row turns ready once the token arrives. It shows only when your team runs a board, and on the Mac that created the org only when that Mac holds the switchboard admin token, in which case `rt team peer` connects its board. It shows an error with a **Re-check** when the switchboard does not answer.

## Connecting the admin's board

A Mac that holds the switchboard admin token connects its own board: `rt team create` does it for you, and `rt team peer` does it later, for example when the create could not reach the switchboard. It registers the board under the username this Mac recorded for the org, and leaves a board that already peers alone. On that Mac, the **Board peering** row's steps name `rt team peer`. `rt team status` counts the members with a connected board, and its `--json` marks each member's board as peered or not.

`rt team members remove <handle>` removes them from the org and also disconnects their board from the switchboard, so it stops receiving the org's peer traffic. When this Mac cannot disconnect it, the command says so and names who can.

## Switching teams

When the roster puts you on more than one team, pick the one you work as in **Settings → Team → Your team**, or:

```bash
rt team use gadgets
```

Your settings then read that team's folder over the org's, and its pack is turned on in place of the old one.

## When an invitee replies

While you have outstanding invites, the daemon checks each one for a reply every few minutes and notifies you once per reply. The notification's **Add member…** action runs `rt team members sync`, which adds the invitee's key so the org's secrets decrypt for them.

## How changes travel

The daemon keeps each Mac's clone in step with the org repo. It pulls on a timer, and on an admin's or owner's Mac it also commits and pushes the changes that Mac's role owns, such as a `rt settings set --scope org` or `--scope team` write, with no hand commit. It does this only on the org's data branch, or on a [trial branch](#trying-a-change-on-a-branch) you chose; on any other branch the **Org branch** row in setup status says it is paused. Packs are the exception: the pack's author commits and pushes a pack's edits, and `rt skills sync` brings the installed copies current. A member's Mac only pulls, so its clone never drifts from the org's.

## Trying a change on a branch

Your clone of the org follows whatever branch it has checked out: the daemon syncs that branch, `rt team publish` pushes it, and your apps read it. Everyone else stays on the data branch, so an org owner or admin can try a breaking change without touching their Macs:

```bash
rt team branch use org-trial
```

When the org repo has no `org-trial` branch, rt makes it from the data branch's published tip. It then switches your clone in place, and the daemon commits your changes there, on this Mac only. The switch holds while your clone has unsaved changes or unpublished commits, and it refuses a branch that holds no org data.

Make and test the change, then merge `org-trial` into the data branch on your forge, and switch back:

```bash
rt team branch use mattstack
```

`rt team status` names the branch when your clone is not on `main`. `rt team invite` refuses on a trial branch, because the people you invite clone the data branch.

An org that still keeps its data on `main` has no data branch to start from, so there `rt team branch use` switches only to a branch that already holds the org's data, such as one the move script made. `rt team branch use main` switches back.

## Moving to a data branch

An org made before v2.25.0 keeps its data on `main`. An org admin moves it onto its own branch once, from a mattstack checkout:

```bash
bun scripts/move-to-data-branch.ts ~/.mattstack/orgs/<org> --admin <username>
```

On its own it prints the plan and writes nothing. Run it again with `--write` to make the move. It refuses unless your clone is clean and matches the org repo's `main`. It makes the data branch, `mattstack` unless `--data-branch` names another, with the org's data and a README. Then it commits the pointer to `main`. When `main` refuses the push, the pointer goes to a `mattstack-pointer` branch instead; land it the way your repo takes changes, such as a merge request.

To try the move first, give the data branch a trial name and leave `main` alone:

```bash
bun scripts/move-to-data-branch.ts ~/.mattstack/orgs/<org> --admin <username> \
  --data-branch org-trial --no-pointer --write
rt team branch use org-trial
```

No other Mac moves. The real move refuses when the org repo already has its data branch, so never try it under the name you will keep.

Once the pointer is on `main`, each member's Mac on an updated app moves its clone onto the data branch by itself, at its next pull or `rt team pull`. Unpublished org commits move with it. Uncommitted changes, a detached HEAD, or commits outside the org's data hold the move, and the **Org layout** row says which. A member's app that cannot read the new layout holds at the last commit it can read, and the row says to update the app.

## Renaming your org

The org's name is what its repo says it is, not the folder on any one Mac. An org owner renames it with:

```bash
rt team rename gadgets
```

The rename refuses when your clone has uncommitted changes to tracked files or is behind the org repo, the same as `rt team publish`. It commits the new name on the branch your clone has checked out, pushes it, and moves your own folder to `~/.mattstack/orgs/<new name>/` right away. Team folders, packs and the marketplace's name stay as they were.

Each member's Mac follows at its next setup check after an app update. To follow now, run:

```bash
rt setup update --force
```

Until then their clone keeps the old folder name and everything keeps working. The **Org folder** row in setup status says the folder has not caught up yet.

### Moving from the old folder

Older versions of mattstack kept the org under `~/.mattstack/teams/<org>/`. The first setup check after an update moves it to `~/.mattstack/orgs/<org>/`, along with rt's record of it, the repo list and the Claude marketplace that serves your packs. Nothing in the org repo changes. The move cannot run while the clone has uncommitted changes to tracked files or a rebase in progress. Untracked files move with the folder. When the move is blocked, the setup check's notification and the output of `rt setup update --force` say what is in the way. The **Org folder** row only says the folder has not moved yet. Fix it and run `rt setup update --force`.

## Forge access

Who can reach the org's repo on the forge follows the org's roles:

| Role | Repo access | Pushes the data branch |
|---|---|---|
| Org owner, admin, team owner | Write (GitHub write, GitLab Developer) | Yes |
| Member, or on no team | Read (GitHub read, GitLab Reporter) | No |

rt changes the forge only after an admin lets it, on their own Mac:

```bash
rt team manage-membership on    # rt manages forge access from this Mac
rt team manage-membership off   # you manage it yourself
```

With it on, rt protects the org's data branch the first time, keeps its push list to the people above, and gives each person the repo access their role needs. It does this a few minutes after a roster or role change, and again at each app update. It never lowers anyone's repo access. Someone who loses a role or leaves the roster only comes off the data branch's push list. `rt team members remove` is what takes repo access away. rt never changes the rules of any other branch. It never touches the repo access of people who are not on the org's roster, such as developers who use the same repo for code.

While your Mac is on a trial branch (`rt team branch use`), rt leaves forge access alone until you are back on the org's data branch.

To see the difference, or to change the forge now:

```bash
rt team forge-access
rt team forge-access --apply
```

On an admin's Mac the **Forge access** row in setup status shows the same difference. When the forge refuses a change, because your account can't administer the repo, the row shows the step to do by hand.

rt manages forge access once the org's data has a branch of its own.

:::note
GitHub limits pushes to named people only on a repo an organization owns, and protects a private repo's branches only on a paid plan. GitLab names people on a protected branch only on Premium and Ultimate. Where the forge can't, anyone with write access can push the data branch, and only rt limits what they change there. The row says so.
:::

## Team packs

Your team's pack is installed during setup but is **not enabled** by default. The daemon's snapshot engine converges your team's pack on every pull that moves HEAD: for a pack that is already installed it runs `claude plugin update` (preserving the disabled state), never `install` (which would re-enable). Other teams' packs are left alone.

The checklist (**Setup status…**, or `rt setup status`) shows a row per team-served pack with its installed version, served version, and the command to enable it.

### A pack that needs a newer app

A pack can need a newer mattstack app than the one on your Mac. When it does, rt holds the pack back: if you already have it, you keep your installed version, and if you don't, nothing is installed. The mattstack plugin is held the same way. The pack's row on the checklist (the **Claude plugins** row, for the mattstack plugin) says so:

> widgets 0.11.0 needs a newer mattstack app (engine 0.31.0 or later). Update the app when it's offered.

The row has no button, and it never blocks **Install**. Once you update the app, the next pull or launch installs the held version with no other step.

`rt --version --json` shows the engine your app runs, beside rt's version.

## Pulling now

```bash
rt team pull
```

Asks the daemon to pull the org clone immediately instead of waiting for its periodic pull. When the pull moves HEAD, your team's pack converges exactly as above.

`rt skills sync` is for a pack's author: it pulls the pack and engine checkouts, recompiles and pushes a new version when the compiled skills have drifted, and updates the installed plugins. When the mattstack engine is installed from its marketplace rather than a local checkout, sync first updates that installed copy from its marketplace, stops if the update fails, and compiles the pack against it. When the engine on main needs a newer app than yours, sync stops and tells you to update the app first.

## Quick reference

| Command | What it does |
|---|---|
| `rt team create <name> [--first-team <team>]` | Start an org with its first team inside |
| `rt team add <team> --owner <user>` | Admins: add a team with its owners |
| `rt team use <team>` | Switch which of your teams you work as |
| `rt team publish` | Push your org changes to the remote |
| `rt team rename <name>` | Org owners: rename the org; members follow at their next update |
| `rt team branch use <branch>` | Org owners and admins: switch your clone to a trial branch, or back |
| `rt team invite --handle <user> [--teams <team>]` | Admins: mint an invite that puts someone on a team |
| `rt team manage-membership [on\|off]` | Admins: let rt manage forge access from this Mac |
| `rt team forge-access [--apply]` | Admins: see and fix who can reach the org's repo on the forge |
| `rt team join` | Redeem an invite code |
| `rt team members sync` | Admins: collect reply keys from invitees |
| `rt team members set <user> --teams <team>` | Admins: change which teams someone is on |
| `rt team members add <user> --to <team>` | Team owners: put someone in the org on one of your teams |
| `rt team members drop <user> --from <team>` | Team owners: take someone off one of your teams |
| `rt team members remove <user>` | Admins: revoke access and re-encrypt |
| `rt team status` | Show the org and your team |
| `rt team pull` | Pull the clone via the daemon, converging your team's pack if HEAD moved |
| `rt skills sync` | Pack authors: recompile, push, and update a pack's plugins |
