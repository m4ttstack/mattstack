# Install

rt ships inside **mattstack.app**, the mattstack menu bar app. Installing the app installs rt, the daemon, and everything else in the suite.

## Requirements

- A Mac with Apple silicon or an Intel processor. The app is a universal build.
- macOS 14 or newer.
- Xcode Command Line Tools with git 2.35 or newer. Setup starts installing them on its first screen, and updates older ones.

## Install the app

1. Download the `.dmg` from the [latest release](https://github.com/m4ttstack/mattstack/releases/latest).
2. Drag **mattstack.app** to `/Applications` and open it.
3. The setup window opens.

Nothing asks you for anything before the setup window: no notification prompt and no login item. You answer every question first, wait once if your team admin has to approve you, and then one progress bar sets up the Mac while you do something else.

## Three things from macOS

The first screen is **Three things from macOS**. It moves on by itself once all three are done.

| Row | What it lets mattstack do | What you do |
|---|---|---|
| **Full Disk Access** | Reads your repos and Chrome's profile | Click **Open settings** and turn on mattstack. mattstack reopens itself once it's on. |
| **Notifications** | Tells you when setup is done | Click **Allow**. |
| **Fancy URLs** | Grant mattstack apps permission to use .mattstack | Click **Allow** and enter your password in the macOS dialog. |

**Allow** on **Fancy URLs** installs the local proxy behind addresses like `board.mattstack`. The macOS admin dialog installs it. macOS then asks once more, in its own Certificate Trust Settings dialog, to trust the proxy's certificate. Both happen here, so the run never stops for a password. mattstack never stores the password. See [The local proxy](/rt/guides/proxy).

While you're on this screen, the Command Line Tools start downloading in the background. A later screen shows a **Git tools** row while they install.

Older Command Line Tools can carry a git too old for setup. The **Git tools** row then names the version and offers **Update**. When macOS offers no update, remove the old tools and install them again: in Terminal, run `sudo rm -rf /Library/Developer/CommandLineTools`, then `xcode-select --install`. If a run already stopped on old git, **Show steps…** on its paused screen gives the same steps.

## How are you setting up?

Pick one card:

- **Join a team**: a teammate sent you an invite. See [Paste your invite](#paste-your-invite).
- **Create a team**: start a team that others join later. See [Create a team](#create-a-team).
- **Just me**: one person on one Mac, no team repo. See [Just me](/start/setup#just-me).
- **Move from another Mac**: bring your own settings over. See [Move from another Mac](#move-from-another-mac).

## Paste your invite

1. Paste the invite code. When you opened mattstack from the invite link, the code is already there. Once mattstack reads it, the screen names the team and who invited you, for example **Mithrandir, invited by Jane Doe**.
2. When your team's forge needs a token, paste one into the token row. Its subtext says what it's for: "Lets mattstack reach the team's repo and open MRs" (PRs on a GitHub team). GitLab always needs a token. GitHub needs one only when the `gh` CLI isn't signed in.
3. Click **Join**. mattstack sends your request and moves to the wait.

**Create token** opens the forge's new-token page with the scopes rt needs already checked:

| Forge | Joining a team | Owning a team |
|---|---|---|
| GitLab | `api` | `api` |
| GitHub (classic token) | `repo`, `read:org` | `repo`, `read:org` |

On GitLab, rt requires only `api`. The link also checks `read_api`, `read_user`, `read_repository`, `write_repository`, and `ai_features`. rt refuses a token that lacks a scope, and names the scope. A GitLab member needs `api` because the board posts review comments and replies on MRs as you. The GitLab link targets GitLab 16 or newer.

### A self-hosted GitLab

mattstack shows the GitLab host your team declares, but never sends a token to it until you confirm it. The token row then reads **Connect gitlab.example.com from the terminal first**. Confirm the host once from a terminal, then come back to the window:

```bash
rt setup gitlab connect --host gitlab.example.com
```

## Waiting for your team admin

After **Join**, the screen shows your team's name and reads **Waiting for Jane Doe to confirm your membership**. Let them know you're waiting. Your admin approves from the notification mattstack shows them.

The wait has no progress bar, because nothing installs for the team until your admin approves you. Click **Hide** to close the window; mattstack keeps checking in the background. When your admin approves, a **You're in** notification brings you back. Once they approve, mattstack starts installing what the next screen's sign-ins need, such as Claude Code and any team tool with a sign-in.

A request nobody has approved yet keeps waiting.

## Connect your accounts

**You're in. Connect your accounts** lists what your team uses, one row each. Most rows open your browser. **Continue** unlocks once each one is connected.

| Row | What it lets mattstack do |
|---|---|
| Your forge (GitLab or GitHub) | Already done: **Connected as janedoe from your invite** |
| **Slack** | Lets mattstack track and post MRs in Slack (PRs on a GitHub team) |
| **Claude** | Runs your agents. "You know, to do agentic stuff." |
| A team tool with a sign-in, such as Doppler | For running your dev servers |
| **Linear**, when your team uses it | So mattstack can read and write Linear tickets |
| **Fast Browser** | Lets agents drive your real Chrome |

- **Connect Slack** opens Slack's Allow page in your own browser, where you're already signed in. The row ticks itself off when Slack hands back.
- **Sign in to Claude** reads **Installing…** until Claude Code is on the Mac, then opens Claude's sign-in in your browser. When the browser shows a code, paste it into the row and press **Sign in**.
- Board agents run Claude Code from `~/.local/bin/claude`. When Claude Code is installed somewhere else, such as by Homebrew, or the install failed, the row offers **Install**, which installs it there with Claude's own installer.
- A team tool's **Sign in** also waits for its install. When the tool shows a code, the row reads **Your code is ...** so you can confirm it in your browser.
- **Linear** takes a token. **Create token** opens Linear's page for one.
- **Add to Chrome** opens the Fast Browser extension's Chrome Web Store page. The row reads **Waiting for Chrome…** and turns to **Added** by itself. Without Chrome, the button reads **Get Chrome** first.

When your team declares another account that setup needs and the run can't set up for you, it gets a row on this screen too.

## Last bit: this Mac

**Where Mithrandir's repos and your settings live** has two parts.

**Your repos** has one row for each repo your team tracks, and each asks one question first: **Clone it fresh** or **Already on this Mac**. rt looks for an existing checkout in the usual places, up to two folders deep. `~/Developer`, `~/Projects` and `~/repos` are among them. When it finds one, **Already on this Mac** is picked for you and the row shows what rt found. Otherwise nothing is picked until you choose. **Choose its folder…** appears only when you say the repo is already on this Mac and rt didn't find it. A git worktree never counts as a checkout: rt refuses one and names the main checkout to pick instead. The board's repo says **The board starts here**: the board's agents start in that checkout.

**Your settings**: mattstack keeps your settings in one folder, your home repo at `~/.mattstack/user`. Two tiles pick where it lives, and neither is picked until you choose:

- **Store in a GitHub repo**: "Private. A new Mac restores from it."
- **Store on your Mac**: "Your settings won't be backed up."

After **Store in a GitHub repo**, a **Remote repo** row appears:

- When `gh` or rt's own GitHub sign-in can already create repos, the row offers **Create a private GitHub repo** right away.
- On a Mac with no GitHub token, such as a Just me Mac or a GitLab team's, the row offers **Sign in to GitHub** ("Opens your browser once. rt then makes a private repo for you"). Your browser opens `github.com/login/device`, and the row reads "Your code is XXXX-XXXX. Confirm it in your browser" with **Open again**. Once you confirm, it reads "rt creates it as a private repo when setup runs".
- A stored GitHub token that can't create repos still gets a field for the repo's URL.

When your settings folder already has a remote another Mac can restore from, the row shows that remote and rt creates nothing. A remote rt can't restore from, such as a local folder, gets a field for a new URL instead.

Otherwise rt names the new repo `mattstack-home`, or `mattstack-home-2` to `-5` when that name is taken. It's private, and the `gh` CLI isn't needed.

You can set a different or non-GitHub repo later with `rt home remote set <url>`.

Click **Set up this Mac**. The footer says it takes about 10 minutes.

## Setting up this Mac

One progress bar runs the rest: a playful word such as **Bloviating…**, a percent, and the time left. Nothing needs you, so close the window if you like, or click **Hide**. A notification says when the Mac is ready.

The run:

- links `rt`, `fast-browser`, `gitq`, and `deck` into `~/.local/bin`, puts that folder first on your PATH, and adds the `rtcd` alias to your shell
- registers the rt daemon and deck (which serves the bundled apps) as background services and starts them
- clones the repos set to **New checkout**
- points the board at its repo, so the board's agents start in that checkout. The board's repo is the first repo in the team's board projects, else the first repo the team tracks
- installs the mattstack Claude Code plugins, turns on your team's pack, and seeds Claude Code's permissions (see [Claude Code setup](#claude-code-setup))
- writes the **sparse** writing style on a new Mac where nothing chose one
- installs the `rt-context` and `skill-blocks` editor extensions into every VS Code-family editor it finds
- restarts the apps deck manages, so none keeps running code from before the run

The bar never opens a browser or raises a dialog. When a step would need you, the bar stops instead.

### Setup paused

When a step fails, the screen reads **Setup paused**. It says what failed and why, for example "Couldn't clone your repos" and "GitLab says your token can't see acme/acme-api". Everything before that step is done. Fix the cause, then click **Retry**. **Show log** shows what the step printed. When macOS holds mattstack's background item, the paused screen offers the button that approves it in Login Items.

### When the app quits or relaunches

Setup picks up by itself. mattstack saves each answer as you give it, so a relaunch mid-form loses nothing, and a run that was going resumes on its own. App updates wait while setup runs, with the window open or not.

## This Mac is ready

The last screen reads **This Mac is ready** and **Go make something cool**. **Open the board** finishes setup and opens the board (**Open the console** on a Just me Mac). Closing the window here finishes setup too.

Finishing starts herdr, the terminal server your agents run in, and adds mattstack to your login items. If herdr cannot start, a notification says why and how to try again.

## Create a team

**Create a team** asks for the team's name, where its settings live (GitLab or GitHub), and the group (on GitHub, the owner) its repo goes in. mattstack creates the team's repo there with your token. On GitHub with the `gh` CLI signed in, no token is needed. Click **Create team**. No wait follows: you go straight to the account and this-Mac screens, plus a **Slack app** row, which one owner makes once so the team can connect Slack. See [Teams and invites](/start/teams#creating-an-org).

## Move from another Mac

1. Type your backup repo, for example `janedoe/mattstack-home`.
2. Paste your recovery key. On your old Mac, `rt home key export` prints it.
3. Click **Restore**.

Restore puts the recovery key in your keychain, clones your settings, and starts the progress bar. rt refuses a key that can't open the backup, and leaves your keychain as it was. When this Mac already holds a different recovery key, rt never replaces it on its own: run `rt home key import --force` with the key from your old Mac, then click **Restore** again.

## After setup

**Setup status…**, just under **Settings…** in the menu bar menu, reopens the setup window on whatever screen needs you, such as **Connect your accounts** when a token expired. With nothing to do, it shows **This Mac is ready**. When a step the last run couldn't finish is all that's left, the window lists it under **Still to do** with its own button, and the footer reads **Finish setup**: fix the row, and setup finishes on its own. Until setup is finished, the same spot reads **Resume setup…** and reopens the window where you left off.

**Settings…** holds the rest. See [The menu bar app](/start/menu-bar-app). Three things live only there, and none of them holds up setup:

- **Mission Control shortcut**: Settings → General → Keyboard.
- **Skill overrides**: Settings → General, only when a hand-edited overrides file still uses old key names.
- **Chrome sign-in**: Settings → Fast Browser, only when a team pack needs Chrome signed in to a site.

Your **writing style**, the voice agents use for what they post under your name, is in Settings → General. A new Mac starts on sparse.

## From a terminal

To set up without the setup window (a VM, CI, or a scripted install), run the same steps from the CLI. mattstack.app still registers the background services and the proxy, so keep it running:

```bash
# run from /Applications, not the DMG
/Applications/mattstack.app/Contents/MacOS/rt --post-install
rt setup status    # every setup row, as text
rt verify          # read-only health report
```

Each answer in the window has a CLI form:

```bash
rt setup gitlab connect            # or github, linear, slack, sdm
rt setup gitlab connect --host gitlab.example.com   # confirm a self-hosted GitLab
rt setup repo place github.com/acme/widgets --checkout ~/code/widgets   # or --clone-to <folder>
rt setup repo-root set ~/code      # Just me: the folder new clones go in
rt home remote set <url>           # or --create
rt home restore janedoe/mattstack-home --stdin   # move from another Mac; the recovery key on stdin
rt skills writing-style use <id>   # omit the id to pick
```

Until setup has run, other `rt` commands print a one-line hint pointing at mattstack.app or `rt setup install`.

## Claude Code setup

Setup seeds a baseline `permissions.allow` list into every Claude Code config dir. Agents then don't stall on per-tool prompts for calls rt already trusts:

- The mattstack MCP server and the Fast Browser plugin.
- `EnterWorktree`.
- `claude plugin update`.
- The few rt commands skills still run in a shell (`rt gate` and `rt events wait`).

Everything else a skill runs routinely is a tool on the [MCP server](/skills/mcp). Existing entries stay; rt adds only missing ones. A config dir with no `permissions.defaultMode` gets `auto`, and a mode you already chose stays. A config dir with no `tui` setting gets `"tui": "fullscreen"`, the Claude Code layout rt's pane tools expect. To change it back, remove the `tui` line from that dir's `settings.json`; an update does not put it back.

It installs the `mattstack`, `fast-browser`, and `chat` plugins from the mattstack marketplace, and `superpowers` from `claude-plugins-official`, which the mattstack skills and every team pack call. An existing `superpowers-marketplace` install counts.

## What gets installed

| Component | Description |
|---|---|
| `mattstack.app` | Menu bar app: setup, daemon health, notifications, updates. See [The menu bar app](/start/menu-bar-app) |
| `rt` | Ships inside the app (`Contents/MacOS/rt`), linked at `~/.local/bin/rt` |
| Background daemon | Caches branch and MR data, scans ports, guards git hooks, snapshots the home repo. See [The daemon](/start/daemon) |
| Bundled apps | board, console, chat, and boxscore, served locally through deck |
| `rt-context` extension | Every VS Code-family editor: worktree, branch, and linked ticket in the status bar. See [Editor extensions](/rt/guides/context-extension) |
| `skill-blocks` extension | Every VS Code-family editor: errors, hover, completion and rename while you write skills. See [Editor extensions](/rt/guides/context-extension) |
| Shell integration | `~/.local/bin` first on PATH, plus the `rtcd` alias, for zsh, bash, and fish |
| Bundled helpers | `jq`, `gh`, `glab`, `bun`, `node`, `sops`, `age`, `zstd`, `git-lfs`, `cloudflared`, `fast-browser`, `gitq`, and `deck`, among others, pinned and shipped inside the app |

Helpers resolve by absolute path inside the app bundle. The ones meant to be typed (`rt`, `fast-browser`, `gitq`, `deck`) are linked into `~/.local/bin`.

`rt setup status` reports **PATH precedence**: whether `~/.local/bin` comes first on your PATH through rt's own line in `~/.zshenv`, so your shell finds rt's shims and team intercepts before any conflicting binary. It reads PATH the way a new terminal tab sees it, from a fresh login shell, not from the app.

## Updates

mattstack.app updates itself through Sparkle. **Check for Updates…** in the menu bar menu checks on demand. After an update, the app brings your setup forward on its own with `rt setup update`; see [Updates](/start/menu-bar-app#updates) in the menu bar app guide.
