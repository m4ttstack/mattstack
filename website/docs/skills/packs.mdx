# Packs

A pack is your team's plugin: the verbs your team types (`/<team>:work`), the bindings that route each pipeline stage to your rules, and the rules themselves. Nobody writes it by hand. Two skills do the work: `mattstack:creating-a-pack` and `mattstack:extending-a-pack`. The examples here use an org called `acme` and its team `widgets`.

A team does not fork the plugin. Its pack compiles a `work` verb from the plugin's engines with nothing bound, so the generic pipeline runs on day one, and rules arrive later one at a time.

Each engine is a tree of blocks: an `index.block.md` root and one `*.block.md` file per section. A section is a step of the flow, the domain rules, or another part of the verb. A block that takes your team's text declares a prop, and a pack fills a prop by binding a fill to it. A fill is a small skill in your team's words. [`rt skills blocks`](/rt/reference/skills/blocks) shows a verb's blocks and their props.

## Before you start

On the machine that runs it you need the rt daemon, the mattstack and superpowers plugins, `glab`, and a GitLab remote on the repo. Your org must be on the machine too: `~/.mattstack/orgs/<org>/`, with one folder per team. With no org yet, `rt team create` makes one; see [Teams and invites](/start/teams). An org admin gives another team its folder with `rt team add`.

## Create the pack

In the repo, say what you want in plain words:

```
$ claude
> we want the mattstack work pipeline on this repo, our team is widgets
```

`mattstack:creating-a-pack` runs the checks above and stops on any miss, naming the fix. Then it runs `rt skills init`, which writes the pack in your team's folder of the org clone, compiles it, checks it and installs it on your machine. The pack starts with no rules, and every stage runs its generic path.

Init also publishes the pack: it commits the new files in the org clone and pushes them. When that falls short, `rt team publish` finishes it. Your team's members receive the pack through `rt setup`, and a machine installs only its active team's pack.

## Prove it

`/widgets:work` appears after `/reload-plugins` in your Claude session. Run the pipeline on a small real ticket:

```
> /widgets:work <ticket>
```

A good first run shows a branch or worktree, an `APPROACH:` block at the plan gate, a commit, an MR and a CI verdict. The stages tell you where they took a generic fallback. Until this run has happened, the pack is scaffolded, not proven, and the skill says so.

It then asks one question, once: are any of your team's rules already written down (CONTRIBUTING, a review checklist, branch rules, a release checklist)? "No" is a complete answer.

## Add a rule

Every rule is one round of `mattstack:extending-a-pack`, one ask at a time:

```
$ claude
> our pipeline shipped an MR without running bun run lint; make ship run lint before it opens an MR on this repo
```

The skill sorts the ask into one of five places:

| The ask is about | Where it lands |
| --- | --- |
| A rule that holds even outside a pipeline (branch names, forbidden ops, where things live) | `skills/context/SKILL.md`, a public skill in the pack |
| Something one stage or verb should do differently | A fill bound to a prop on one of that engine's blocks: the step's block for a rule at one step, `domain-rules` for the whole stage |
| A new door: `ship`, `review`, `watch-ci`, `self-review`, `receive-review`, `shepherdr` | A roster entry in `pack/stubs.jsonc` |
| The wording of an existing verb | Its `description` in `pack/stubs.jsonc` |
| One kind of work (accessibility, a bug fix) that runs its own stages or fills | A specialized pipeline in `pack/skills.jsonc` plus a `work-<kind>` verb that runs it |

For the lint example, you see a failing run first, with nothing running lint. Then a small fill skill written in your team's words is bound to the fast-checks step of the ship stage:

```bash
rt skills bind stage-ship stage-ship/domain-fast-checks rules widgets:lint-changed --pack widgets
```

A pack that also has a `ship` verb binds the same fill to that verb's own block, `ship/flow/domain-fast-checks`. `tests/certify.sh` and `rt skills check` pass, and the same task runs again with lint blocking the push. Publishing goes through `mattstack:editing-skills`: bump the pack version, commit, push, `rt skills sync --pack widgets`, `/reload-plugins`. A rule is undone the same way: remove the binding and the fill, bump, publish.

## Add a specialized pipeline

The pack starts with one pipeline, `feature`, and `/widgets:work` runs it. To give one kind of work its own stages or its own fills, ask `mattstack:extending-a-pack` for a specialized pipeline. The pipeline and its first override fit in one round, with one publish at the end. It:

1. Declares the pipeline in `pack/skills.jsonc`, say `accessibility`, starting from a copy of `feature`'s stage list. A pipeline a work verb runs starts with `stage-provision`, ends with `stage-watch-ci`, and includes `stage-implement` and `stage-ship`.
2. Runs `rt skills materialize`. Compile, check and bind read the pack's bindings file for your repo, not `pack/skills.jsonc`, so the new pipeline exists for them only after this step.
3. Adds a verb that runs it inside the `verbs` object of `pack/stubs.jsonc`, next to `work`, named `work-<kind>` so it groups under `/widgets:work`. rt reads no entry outside `verbs`:

   ```jsonc
   {
     "verbs": {
       "work": { "engine": "work", "description": "..." },
       "work-a11y": {
         "engine": "work",
         "pipeline": "accessibility",
         "description": "Use when running accessibility work end to end"
       }
     }
   }
   ```

4. Puts the verb on the pack's surface with `rt skills surface set work-a11y --public`, which also compiles the pack, then checks it.
5. Binds each fill that differs for that pipeline with `rt skills bind <stage> <block> <prop> <fill> --pipeline accessibility`. Every stage it does not override runs the default fills. Where a pipeline's fills differ, compile writes a stage copy such as `attachments/stage-evidence--accessibility/`.

`/widgets:work-a11y` then runs accessibility work, and its runs record the pipeline `accessibility`. Each verb resumes only runs of its own pipeline.

To put a pipeline's prop back on the default fill, ask the same skill to undo the override. It runs `rt skills bind <stage> <block> <prop> --pipeline accessibility --unset`, checks the pack and publishes. The recompile removes the stage copy once that stage matches the default again. [`rt skills bind`](/rt/reference/skills/bind) has the details and refusals.

## Add browser evidence

For screenshots of your app as evidence, ask `mattstack:extending-a-pack` for browser evidence. It adds a `## Browser target` section to the pack's evidence fill, with facts about your app and no steps:

| Block | What goes in |
| --- | --- |
| Reach the view | How the servers start, the URL the app answers on, where the saved login is, the URL for a case, the state to set up first |
| What proves a change | Which view and elements show each kind of change, and what to ask you at intake |
| Captions | How labels and the claim are worded |
| Personal data | What is always hidden, and what may show |

Leave a block out and it takes its default. The URL comes from the plan, and you sign in. The plan's words describe the case. Captions use plain words. Every personal detail that the case does not verify is hidden.

The evidence and ship stages do the rest. They get the app ready and hand Fast Browser every case of the pass at once. Fast Browser captures each page and composes an evidence board: one cropped, labelled image. Then one question asks about the pass's boards together. Look at each board and each hidden crop, then confirm that nothing on them should stay private, or name the board that needs more hidden. A board can't be uploaded until you confirm. A board that hides nothing must be confirmed too, unless Personal data says the page's source holds only mock data.

The run keeps each evidence board with its captures. Before anything is uploaded, ship shows you every board it is about to attach, as thumbnails in the console or opened from the terminal, and asks before it attaches them to the MR. It skips a board you already confirmed, and a mock-data board, unless the board was captured again or revised since. A ticket image the run saved as a case's before is never uploaded as it is, and neither is a copy of it or an imported capture of it; its evidence board is.

## When a pack needs a newer app

`rt skills compile` writes the floor of the mattstack engine it compiled against into the pack's `pack/requires.json`, or a higher one when the pack uses [team values](#which-app-it-needs). The floor is the oldest mattstack app that can run the pack. A teammate whose app is older keeps the pack version they have, or gets none yet, until they update the app; see [Teams and invites](/start/teams#a-pack-that-needs-a-newer-app). `rt skills check` reports a missing or stale `pack/requires.json` as drift. `rt skills init` stops when your own app is older than the floor, and tells you to update the app first.

## Paths into another skill

A fill or engine that names a file in another skill or attachment uses a placeholder, never a hand-typed path. `rt skills compile` stops on a hand-typed path into `attachments/`, `skills/` or a sibling skill's folder, such as `../../attachments/capture-evidence/SKILL.md` or `${CLAUDE_SKILL_DIR}/../ship/SKILL.md`. The error names the file and line, and the placeholder to write when compile can tell which one fits:

- For a file in another attachment or source skill, write `{{pack.path:<attachment>/<file>}}`. Compile checks that the file exists.
- For a compiled verb's `SKILL.md`, write `{{verb.path:<verb>}}`. Compile writes the path from the compiled file to that verb, whichever side each one lands on.

A path inside the skill's own folder, such as `${CLAUDE_SKILL_DIR}/scripts/run.sh`, is fine.

A compiled skill never reads pack source through `pack.path`. Compile copies the whole attachment into the compiled skill's own `references/<attachment>/` folder and writes the path to that copy, such as `${CLAUDE_SKILL_DIR}/references/capture-evidence/SKILL.md`. Each compiled skill gets its own copy, and every compile replaces it. In a copied `.md` file, compile fills in `{{pack.name}}`, `{{include}}`, `{{verb.path}}` and `{{pack.path}}`. A `pack.path` there copies that attachment too. Other text in braces, such as `${{ secrets.TOKEN }}`, stays as written. A placeholder that depends on the skill reading it, such as `{{stage.dir}}`, stops the compile. Compile copies other files as they are. A link between files in a copied attachment must stay inside that attachment or use `{{pack.path:<attachment>/<file>}}`, because the copy sits in a different folder.

Base text can pick the attachment by team value: `{{pack.path:{{team.gates-fill}}/SKILL.md}}`. This is the only place one marker may sit inside another. The team marker is the whole attachment name, and it cannot be optional. Compile fills in the team's value first, then checks the path like any other `pack.path`. A hand-typed path such as `../../attachments/{{team.gates-fill}}/SKILL.md` gets that placeholder as its suggestion when the team sets the value and the file exists. Otherwise the error comes with no suggestion.

A team's `pack/sections/*.md` text and `pack/params.jsonc` values may use `{{pack.path:<attachment>/<file>}}` and `{{verb.path:<verb>}}` too. Compile puts the team text into the base text first. It then fills in the path the way that text fills in its own. In a compiled skill, the path points at its `references/` copy. In a copied base attachment, it gets the path a base attachment gets. Compile and `rt skills check` stop on a hand-typed path in a section or a value. The error names the section file and line, or the `params.jsonc` line.

`rt skills check` also reads the pack's hand-written skills, which compile never reads. It fails on each path out of a skill's folder that points at no file.

## What not to do

- Do not edit `skills/work/`, `attachments/stage-*/` (stage copies like `attachments/stage-evidence--accessibility/` included), `pack/requires.json` or an attachment folder holding `compiled.json`: compiled output, overwritten on the next compile.
- Do not edit the mattstack engine in the plugin cache: every team compiles from it, and the next update erases the edit.
- Do not edit a repo's generated `skills.jsonc` under `~/.mattstack/repos/`: `rt skills materialize` regenerates it, and `pack/skills.jsonc` is the source.
- Do not edit a pack in a git worktree or another copy of the org repo. Make every pack edit, with its commit and push, in the org clone, on the branch it has checked out. Materialize reads a pack's fragment only from the org clone. `rt skills sync` refuses a `.worktrees/` or `.claude/worktrees/` folder under the pack.
- Do not copy another team's pack: its fills carry that team's rules.
- Do not write a fill "to have something there": a `rules` prop with nothing bound renders as nothing, which is the correct state until a rule exists.

## Fills the whole org shares

A rule every team follows goes in the org's base pack, a folder the org admin adds by hand at `mattstack/org/packs/acme-base/` in the org repo. A team pack uses it with `"extends": "acme-base"` in its `pack/skills.jsonc`, and its own fills join the base's prop by prop. On a prop that merges with `add`, the team's fill follows the base's; on one that merges with `replace`, the team's fill replaces it. Bindings follow the base at once on every machine; compiled fills follow at the team owner's next `rt skills compile`. The base is never installed, so a base fill reaches a team's verbs by being compiled in. There is one exception. A fill that only `board:*` bindings name is copied into the team pack as well. The board opens a fill by `<plugin>:<name>` while it runs, and compile never inlines a board binding. Materialize then points those board bindings at `<team plugin>:<name>`.

## Files the whole org shares

A fill is text compiled into a verb. A file a skill opens while it runs (a reference, a checklist, a script) has to sit inside the installed team pack, and the base is never installed. So when a team pack extends a base, `rt skills compile` copies the base's attachments into the team pack:

- **What is copied:** every attachment folder in the base that has a `SKILL.md` and is not a fill. A fill's `SKILL.md` carries `metadata.provides`, and compile inlines it instead. When only `board:*` bindings name a fill, compile copies it too. An attachment can sit one group deep, as in `attachments/<group>/<name>/`.
- **A board fill the base cannot deliver is refused:** compile stops when the base binds a `board:*` key to a fill it has no `attachments/<name>/` for, or keeps that fill one group deep, since the board finds `attachments/<name>` only.
- **Where it lands:** the same path under the team pack's `attachments/`. Each copied folder gets a `compiled.json` naming the base, its version and the files compile wrote. That file marks the folder as compile's output: the next successful compile rewrites it, and `rt skills check` reports it as drift when it no longer matches the base.
- **Placeholders:** in a copied `.md` file, `{{pack.name}}` becomes the team pack's plugin name, so a base attachment names a team verb as `{{pack.name}}:ship`. `{{verb.path:<verb>}}` and `{{pack.path:<attachment>/<file>}}` resolve in the team pack, and `{{team.*}}` markers take the team's values (see [Team values in shared fills](#team-values-in-shared-fills)). Any other `{{...}}` text, and every file that is not `.md`, is copied as it is.
- **The team's own folder wins:** compile leaves the team pack's own `attachments/<name>/` alone and copies nothing for that name. A folder is the team's own when it has no `compiled.json` that compile wrote. A data file of that name in another shape does not count. To override a base attachment, delete the copied folder and write your own in its place.
- **Clashes stop the compile:** a base attachment named like one of the team's verbs, one of its hand-written skills, or one of its attachments at another path is an error that names both. Rename one of them.
- **Cleanup:** compile removes a copied folder when the base drops that attachment, or when the pack stops extending a base.

Compile writes and removes nothing when any verb fails to compile, so the copies change only on a compile that succeeds.

Don't edit a copied folder: the next successful compile overwrites it. Edit the attachment in the base pack, bump the base, and compile each team pack.

## Team values in shared fills

Two teams often run the same flow with a few different facts: their Linear team, a ticket prefix, an extra block of CI rules. Keep the flow once in the base, and let each team supply its facts. Don't fork the base fill into a team pack: the copies drift.

Base text carries markers, and compile fills them in from the team pack it is compiling. Markers work in a base fill's body and in the `.md` files of a base attachment copied into a team pack.

| Marker | Compile puts there |
| --- | --- |
| `{{team.<key>}}` | The string at `params.<key>` in the team's `pack/params.jsonc`. |
| `{{team.section:<name>}}` | The contents of the team's `pack/sections/<name>.md`. |

Both are required. Add a trailing `?` (`{{team.<key>?}}`, `{{team.section:<name>?}}`) to make one optional: a team that has not supplied it gets nothing there.

A base fill might read:

```markdown
Look up the ticket in the {{team.linear-team}} Linear team. Its id
starts with {{team.ticket-prefix}}-.

{{team.section:ci-extra-jobs?}}
```

The widgets team pack supplies the values in `pack/params.jsonc`:

```jsonc
{
  "version": 1,
  "params": {
    "linear-team": "Widgets",
    "ticket-prefix": "WID"
  }
}
```

It puts its extra CI rules in `pack/sections/ci-extra-jobs.md`, as plain markdown. A team with no such file gets nothing there, since that marker is optional.

The rules:

- A key or section name uses lowercase letters, digits and hyphens. No key may be named `section`.
- A value is one line. Put a multi-line block in a section.
- A section marker sits alone on its line.
- A value marker can sit inside a sentence or a plain path, but never inside another marker.
- Markers only work in the body of base text. Compile stops on a marker in frontmatter, in a team's own fill, or in a copied file that is not `.md`.
- Neither a value nor a section may contain `{{`, except `{{pack.path}}` and `{{verb.path}}` (see [Paths into another skill](#paths-into-another-skill)).
- An empty value, or a section with only whitespace, counts as missing.

### When a team is missing a value

A pack supplies only the markers in base text it compiles. That means the base fills its bindings use in the verbs and stages it compiles, plus its copied `.md` files. A base fill the team overrides with its own fill asks for nothing. When a required one is missing, `rt skills compile` writes nothing and lists every gap at once:

```
The widgets pack is missing values the acme-base pack asks for
  pack/params.jsonc: linear-team (acme-base:provision-flow)
  pack/sections/ci-extra-jobs.md (acme-base:watch-ci-rules)
```

Add what it lists and compile again. `rt skills check`, `rt skills sync` and the other verbs that compile stop with the same list. A key in `pack/params.jsonc` that no base text asks for is a warning, not an error.

When the base adds a required marker, every team that extends it stops at its next compile until it adds the value.

`pack/params.jsonc` and the sections are pack sources. `rt skills check` reports an edit to them as drift, and `rt skills sync` carries it like a fill edit.

### Starting a pack on a base

`rt skills init --extends acme-base` writes `"extends": "acme-base"` into the new pack. When the base asks the team for values, init adds an empty place for each one and stops with the list. A key gets an empty string in `pack/params.jsonc`, and a section gets an empty file under `pack/sections/`. Fill them in, then run the same `rt skills init` again. It carries on from there and leaves your files alone.

### Which app it needs

Once a pack's base text uses any marker, `rt skills compile` raises that pack's floor to the first mattstack app that fills markers in. Packs that use no markers keep their floor. Start using markers in a base once every member's app has that release.

## Where things live

| Thing | Path |
| --- | --- |
| The org clone | `~/.mattstack/orgs/<org>/` |
| A team's pack | `~/.mattstack/orgs/<org>/mattstack/teams/<team>/plugin/` |
| The org's base pack | `~/.mattstack/orgs/<org>/mattstack/org/packs/<org>-base/` |
| A base attachment copied into a team pack | `.../plugin/attachments/<name>/`, with `compiled.json` |
| A team's values for its base | `.../plugin/pack/params.jsonc` and `.../plugin/pack/sections/<name>.md` |
| The installed copy sessions load | `~/.claude/plugins/cache/<marketplace>/<pack>/<version>/` |

Packs are the exception to the daemon's automatic commits: the pack's author commits and pushes a pack's edits, and [`rt skills sync`](/rt/reference/skills/sync) brings the installed copies current. See [Teams and invites](/start/teams#team-packs) for how a member's Mac receives the pack.
