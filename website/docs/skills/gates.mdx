# Gates

A gate is a daemon-persisted decision that pauses a subject until a human (or another surface) answers it. Gates survive daemon restarts, can be answered from any surface (the in-pane form, the board, the console, or the [MCP server](/skills/mcp)), and the first answer wins via compare-and-swap.

Gates are primarily agent-facing: a herd worker opens one when it needs a decision, the shepherd or a human answers, and the worker resumes. But the CLI surface is how you see what is waiting and answer pending questions directly.

## Lifecycle

1. **Open.** `rt gate open` or `rt gate ask` mints a gate, stores it in the daemon, and emits `gate/opened`. If another open gate already exists on the same subject and kind, it is superseded (closed automatically).
2. **Park** (optional). `rt gate park <id>` marks the gate paused without closing it. A parked gate can still be answered.
3. **Answer.** `rt gate answer <id>` records the answer and releases anyone blocked in `rt gate wait`; a form-presented gate's pane also gets a push (see [Delivery](#delivery)). A second answer to the same gate is rejected cleanly, and the rejection carries the winning answer.
4. **Close.** `rt gate close <id>` closes a gate without an answer. Waiters are released with a "closed" status.
5. **Wait.** `rt gate wait <id>` blocks until the gate is answered or closed. Works across daemon restarts.

## Asking a question with `rt gate ask`

`rt gate ask` is the high-level interface. It resolves the subject automatically, determines the presentation mode, and nudges the operator. The presentation is a form only when the asking session has a pane and every question has at most 4 options; otherwise it is wait, and an over-cap question is reported back as `formCapExceeded`.

```bash
rt gate ask \
  --questions '[{"id":"q1","label":"Which approach?","multi":false,"options":["Refactor first","Ship as-is"]}]' \
  --context "We found dead code in the auth path; removing it simplifies the fix but adds scope."
```

A gate owned by a human (anything not raised from a herd run) must carry `--context`; `rt gate ask` refuses one without it, except for the `milestone` and `pane-attention` kinds.

### Subject resolution

If `--subject` is omitted, the daemon walks a resolution ladder: the session's running run (if exactly one), then the session's agent record's subject. If multiple runs exist, it errors with candidates. Pass `--subject` explicitly to skip the ladder.

### Options

Options can be bare strings or objects with richer metadata:

```json
[
  { "value": "refactor", "label": "Refactor first", "recommended": true, "description": "Removes dead code before the fix" },
  { "value": "ship", "label": "Ship as-is", "description": "Smallest diff, tech debt stays" }
]
```

An option with `recommended: true` gets a "(Recommended)" suffix in the daemon's normalized label, which downstream UI renders as a badge.

### Per-question context

Each question can carry its own `context` field for material specific to that choice. The gate-level `--context` plus all per-question contexts share a single 8 KB budget. When the combined size exceeds the budget, question contexts are dropped first, then the gate context. The response reports `contextOmitted: true` when anything was dropped.

```json
[
  {
    "id": "q1",
    "label": "Which migration strategy?",
    "multi": false,
    "options": ["Blue-green", "Rolling"],
    "context": "The table has 50M rows; blue-green needs twice the disk during cutover."
  }
]
```

### Write-ins

A question can also take an answer in the human's own words. Mark it with `"writeIn": true`, and set it only on a decision question whose free-text answer the agent can act on, never on `next`. The question still needs options; a question with none is free-form already.

```json
{
  "id": "approach",
  "label": "How should we split this?",
  "options": ["One MR", "Two MRs"],
  "writeIn": true
}
```

In the console and the board, the human leaves the options alone and types into the question's note box.

## Answering

```bash
rt gate list --open          # see what is waiting
rt gate answer <id> --answers '{"q1":"refactor"}' --by human   # answer one
```

Answer values must match an option's value verbatim. Free-text feedback rides a per-answer `note` field. For multi-select questions, the answer is an array of values.

A question marked `writeIn` may instead take the human's own words, sent alone with no `value`, `note` or `text`:

```bash
rt gate answer <id> --by human \
  --answers '{"approach":{"writeIn":"migration in its own MR"}}'
```

The daemon refuses an empty write-in, and a write-in on a question not marked for one. The agent treats a write-in as the human's instruction and never maps it onto the nearest option.

### Herd ownership

When a gate was opened by a herd worker, only the owning shepherd's session (or the gated pane itself) can answer it. The shepherd answers or parks one with the `herd_gate_answer` and `herd_gate_park` tools. Pass `--override` to escalate as a human past the automated owner.

## Gates in a pipeline run

A pipeline's skills ask their questions through the gate tools on the [MCP server](/skills/mcp), not the CLI. A stage opens its gate with `gate_ask`, or with `gate_open` from a structured source that the tool fits to the 8 KB budget. When the gate is answered, the answer is recorded on the run as a decision in that stage, so the run's story in [console](/apps/console) shows it. A gate superseded by a later one at the same point records nothing. The gate tools only open, read and record; the skill decides what happens next.

## Delivery

When a gate that carries a nudge session (every form-presented gate does) is answered from another surface, the daemon pushes a notification to the gated pane. The notification tells the pane to re-read the registry; it does not carry the answer itself. The pane then reads the recorded answer. A skill calls `gate_reconcile`, which under a run also records the answer. A shell calls `rt gate wait` (or `rt herd answer`). A gate with no nudge session (a wait-presented `rt gate ask` gate, for one) gets no push: its `rt gate wait` returns.

If the gated pane has exited, the daemon retries delivery with bounded retries (up to 20 attempts). An unanswered herd-owned gate is escalated to the human once its TTL passes, or as soon as the owning shepherd's subscription is gone.

## Subscriptions

`rt gate subscribe` registers a session for push notifications on gates matching a subject prefix. Subscriptions fire on both `gate/opened` and `gate/answered` events and persist across daemon restarts.

```bash
rt gate subscribe --subject-prefix "run:" --session <addr>
rt gate unsubscribe <id>
rt gate subscriptions         # list active subscriptions
```
