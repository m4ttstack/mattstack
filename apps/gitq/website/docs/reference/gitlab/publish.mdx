# gitq publish

Creates a GitLab merge request for each not-yet-published branch in a stack, and updates the merge requests of the branches that already have one.

## Usage

```bash
gitq publish [--stack <name>] [--mr-meta <path>]
```

## Flags

| flag | meaning |
|------|---------|
| `--stack <name>` | Which tracked stack to publish. Optional when the repo has exactly one; required otherwise. See [Global flags](/reference/global-flags#the---stack-rule). |
| `--mr-meta <path>` | Path to a JSON file of `{"<branch>": {"title": "...", "description": "..."}}`. Both fields are required strings for every entry you include. On a new MR, a branch you omit falls back to the branch name as title and an empty description; on an existing MR, a branch you omit keeps the title and description it already has. |

## Behavior

**`publish` creates MRs and updates existing ones.** It walks the stack in topological order and does one of two things per node (`ForgeSync.publishStack`, `src/core/forge-sync.ts:288-409`):

- A node whose `status` is `local-only` **and** whose `mrIid` is still `null` is **created**: pushed, then opened as a draft MR against its parent (`src/core/forge-sync.ts:313-361`).
- A node that already has an open MR is **updated**: the MR is retargeted when the node's parent in the local tree no longer matches what the MR targets on GitLab, and its title and description are rewritten when `--mr-meta` names that branch. The branch itself is **not** pushed (`src/core/forge-sync.ts:363-405`).

A node needing neither is left untouched and does not appear in the results at all. The retarget goes through `ForgeSync.retargetMR` (`src/core/forge-sync.ts:417-427`), the same function you can call on a single branch.

Order of checks, before any network call:

1. **`--mr-meta` is parsed and validated first**, before the store or stack are even touched, so a malformed file fails the same way regardless of stack state or token presence (`src/cli/commands/forge.ts:83-91`).
2. The store loads, the stack resolves, and the stack lease is checked.
3. Only then is the GitLab provider built, which is where the missing-token refusal happens (`createGitLabProvider`, `src/cli/provider.ts:31-35`): `no gitlab token (set GITLAB_TOKEN or add gitlabToken to ~/.rt/secrets.json)`.

Then, before the walk, one read: the MRs of every already-published node, batch-fetched by iid (`fetchPullRequests({ iids, projectPath })`, `src/core/forge-sync.ts:298-305`). An MR's current target is the only way to tell a retarget from a no-op, so publish asks the forge rather than trusting the local `status`. A stack with nothing published yet skips this read entirely, and a failure here fails the whole command before anything is pushed. An MR that comes back merged or closed, or that does not come back at all, is skipped: publish only touches open MRs it could actually read.

For each branch it **creates**, in topological (parent-before-child) order:

1. **Push.** `git push --force-with-lease origin <branch>`.
2. **Create the MR**, as a draft, unconditionally. `sourceBranch` is the node's branch; `targetBranch` is the node's **parent in the local tree**, not whatever it might have targeted before (there was nothing to have targeted, since it had no MR).
3. **Record it.** `mrIid` and `mrUrl` are set, `status` becomes `synced`.

For each branch it **updates**, in the same order:

1. **Retarget**, only when the MR's `targetBranch` differs from the node's parent: `updatePullRequest(projectPath, mrIid, { targetBranch })`, and the node's `status` goes back to `synced`. This is the half that matters after a [`reparent`](/reference/surgery/reparent), which moves a branch locally and leaves its MR pointing at the old parent until publish runs.
2. **Rewrite the title and description**, only when `--mr-meta` carries an entry for that branch. The entry replaces what is on GitLab, including edits made in the UI; omit the branch and its MR prose is left alone.
3. **No push.** A rebased, already-published branch still needs its own `git push --force-with-lease`; publish will not do it for you.

**Stops the walk at the first failure**, create or update alike. It does not attempt the remaining branches, because a child's MR needs its parent's MR to exist first for the target branch to make sense; skipping ahead would create MRs against the wrong base.

Each entry in `results` says which of the two happened: `action` is `created` or `updated`, and an update also carries `changes` (`target`, `metadata`, or both) and the `targetBranch` it now points at. Human output reads `<branch>: created <url>` or `<branch>: updated (retargeted to <parent>) <url>` (`src/cli/commands/forge.ts:66-78`).

`--mr-meta`'s entries are validated up front; a malformed one names the offending branch: `invalid --mr-meta: entry "<branch>" must be {"title": string, "description": string}` (`src/cli/commands/forge.ts:36-53`). Every entry is read, whether the branch is getting a new MR or already has one, so an entry for an already-published branch is an instruction to overwrite that MR's title and description.

With nothing to create and nothing to update, prints `nothing to publish (no branches to create or update)` and exits `0`.

## Exit codes

- `0`: every attempted branch succeeded (including the no-op "nothing to publish" case).
- `1`: a hard refusal (`--mr-meta` malformed, a lease held, no GitLab token, `--stack` unresolved, or the pre-walk read of the existing MRs failing), or completed with at least one failed branch. Check the per-branch `success` field under `--json`, since branches before the failure are already pushed and already have MRs, or already had their MR retargeted. See [Exit codes](/reference/exit-codes) for the shape this shares with `sync` and `reparent`.

Never exits `2`.
