# gitq publish

Creates a GitLab merge request for each not-yet-published branch in a stack.

## Usage

```bash
gitq publish [--stack <name>] [--mr-meta <path>]
```

## Flags

| flag | meaning |
|------|---------|
| `--stack <name>` | Which tracked stack to publish. Optional when the repo has exactly one; required otherwise. See [Global flags](/reference/global-flags#the---stack-rule). |
| `--mr-meta <path>` | Path to a JSON file of `{"<branch>": {"title": "...", "description": "..."}}`. Both fields are required strings for every entry you include. A branch you omit falls back to the branch name as title and an empty description. |

## Behavior

**`publish` only ever creates MRs.** It walks the stack in topological order and acts on nodes whose `status` is `local-only` **and** whose `mrIid` is still `null` (`src/core/forge-sync.ts:259-267`). A branch that already has an MR, however stale its content, is skipped entirely: nothing is pushed for it and nothing about its MR is touched. It never updates or retargets an existing MR: `ForgeSync.retargetMR` exists in source (`src/core/forge-sync.ts:318-328`) but has zero production callers, nothing in the shipped CLI ever calls it. (`README.md:50` and `skills/publish/SKILL.md` both describe `publish` as also updating or retargeting an existing MR; only the create half is implemented.)

Order of checks, before any network call:

1. **`--mr-meta` is parsed and validated first**, before the store or stack are even touched, so a malformed file fails the same way regardless of stack state or token presence (`src/cli/commands/forge.ts:61-69`).
2. The store loads, the stack resolves, and the stack lease is checked.
3. Only then is the GitLab provider built, which is where the missing-token refusal happens (`createGitLabProvider`, `src/cli/provider.ts:31-35`): `no gitlab token (set GITLAB_TOKEN or add gitlabToken to ~/.rt/secrets.json)`.

For each branch it acts on, in topological (parent-before-child) order:

1. **Push.** `git push --force-with-lease origin <branch>`.
2. **Create the MR**, as a draft, unconditionally. `sourceBranch` is the node's branch; `targetBranch` is the node's **parent in the local tree**, not whatever it might have targeted before (there was nothing to have targeted, since it had no MR).
3. **Record it.** `mrIid` and `mrUrl` are set, `status` becomes `synced`.

**Stops the walk at the first failure.** It does not attempt the remaining branches, because a child's MR needs its parent's MR to exist first for the target branch to make sense; skipping ahead would create MRs against the wrong base.

`--mr-meta`'s entries are validated up front; a malformed one names the offending branch: `invalid --mr-meta: entry "<branch>" must be {"title": string, "description": string}` (`src/cli/commands/forge.ts:36-53`). A branch that already has an MR ignores any entry for it in the file: nothing reads `--mr-meta` for a branch the `local-only`/`mrIid === null` filter already excluded.

With nothing local-only to publish, prints `nothing to publish (no local-only branches)` and exits `0`.

## Exit codes

- `0`: every attempted branch succeeded (including the no-op "nothing to publish" case).
- `1`: a hard refusal (`--mr-meta` malformed, a lease held, no GitLab token, `--stack` unresolved), or completed with at least one failed branch. Check the per-branch `success` field under `--json`, since branches before the failure are already pushed and already have MRs. See [Exit codes](/reference/exit-codes) for the shape this shares with `sync` and `reparent`.

Never exits `2`.
