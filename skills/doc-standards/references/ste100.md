# ASD-STE100 digest (Issue 9, January 2025)

Simplified Technical English: 53 writing rules + a controlled dictionary (~900 approved
words). Built in the 1980s so a Polish, Brazilian, and Japanese mechanic read the same
aircraft manual the same way. Today ~64% of adopters are outside aerospace. The official
dictionary requires registration at asd-ste100.org (free); this digest carries the rules
and the dictionary's *principles*, which is what an LLM needs.

## Why it works on LLM output

The rules remove exactly the degrees of freedom LLMs abuse: synonym variation,
subordinate clauses, tense drift, noun pileups, decorative hedging. What remains is
the instruction.

## Word rules (the dictionary principles)

1. **One word = one meaning = one part of speech.** "Oil" is a noun, never a verb.
   "Test" is a noun; the verb is "do a test".
2. **No synonyms.** One approved term per concept, used everywhere. STE approves
   "make sure" — not verify/check/confirm/ensure. Build a project terminology table
   and enforce it.
3. **Approved general words + your own technical names.** STE lets each org add a
   dictionary of approved technical nouns (your product's commands, components, API
   names) and approved verbs. Names are spelled exactly one way (not "the CLI" /
   "the tool" / "the binary" in rotation).
4. **Choose short, common words.** "start" not "commence/initiate", "use" not
   "utilize/leverage", "help" not "facilitate".

## Sentence rules

5. **Procedural sentences ≤ 20 words.** Instructions must fit in working memory.
6. **Descriptive sentences ≤ 25 words.**
7. **One instruction per sentence.** Two actions = two sentences (or two list items).
   Simultaneous actions are the only exception ("Hold the button and turn the key").
8. **Active voice.** Passive hides the actor; docs must say who/what acts.
   Descriptive text allows limited passive when the actor is truly irrelevant — but
   in Markdown docs, prefer active anyway.
9. **Imperative for instructions.** "Run the installer." Never "the user should run",
   "you may want to run", "it is recommended to run".
10. **Simple tenses only: past, present, future.** No present perfect ("has been
    removed" → "was removed in v2.1"), no past perfect, no conditionals-as-politeness.
11. **Keep articles.** Write "install the package", not telegraphic "install package".
    Dropped articles create ambiguity for non-native readers and parsers alike.
12. **Noun clusters ≤ 3 nouns.** "server configuration file backup process" → "the
    process that backs up the server configuration file". If a long cluster is an
    official technical name, hyphenate or define it once.

## Paragraph and structure rules

13. **One topic per paragraph; ≤ 6 sentences.** The first sentence is the topic.
14. **Vertical lists for sequences.** More than ~3 sequential actions in prose →
    numbered list, one action per item.
15. **Tables for parallel data.** Don't narrate what a table shows better.

## Safety-text rules (map to admonitions)

16. **A warning/caution comes BEFORE the step it protects**, never after.
17. **Command form, with the condition first.** "WARNING: Before you disconnect the
    battery, turn the power off." Maps directly to docs admonitions: `> **Warning:**`
    above the step, imperative sentence, one hazard per admonition.
18. **Warning = risk of injury/data loss; Caution = risk of damage/breakage;
    Note = information only.** Never put an instruction inside a Note.

## Quick self-check before shipping a section

- Longest sentence ≤ 25 words? (`check_docs.py` counts)
- Any concept referred to by two different words? (grep both terms)
- Any sentence with two instructions?
- Any "has been / have been / it is recommended / should be"?
- Any 4+ noun pileup?
