# GitHub path for review, respond, doctor and pipeline skills: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every GitHub branch in the review, receive-review, review-posting, ship, stage-ship, stage-evidence and board review/respond skills uses the forge-aware `mr_*` MCP tools instead of `gh`, and board doctor stops plainly on GitHub.

**Architecture:** Skill text only. Plugin engines are block trees under `plugins/mattstack/attachments/`; each graph is Mermaid in the block that carries it, and a judgment node's prose is its own `*.block.md` with `node:` set. Board skills are hand-authored under `apps/board/skills-src/` and expanded into `apps/board/skills/`. Nothing under `lib/`, `packages/` or `plugins/mattstack/attachments/mcp-tools/` changes.

**Tech Stack:** Markdown block trees, Mermaid and dot process graphs, `bun cli.ts skills compile|check|expand`, `plugins/mattstack/tests/certify.sh`, `check-dot.py`.

**Spec:** `docs/superpowers/specs/2026-11-11-gh-skills-design.md` (read it first; its "Tool facts" and "Decided calls" sections are the contract).

## Global Constraints

- GitLab behaviour does not change: every GitLab edge, input and result stays as today. One forge per team.
- No `gh` command anywhere in the edited sources.
- No live forge call of any kind; RED and GREEN agents describe calls against a stated fixture and execute none. No post to any real PR.
- Never run `rt`, the daemon or a built binary against the real HOME, and never set HOME in a command. Compile and check only the CI way: `bun cli.ts skills compile|check` with `--pack-dir` and `--mattstack-dir` pointing at scratch copies (Task 1 gives the commands). Never run `rt skills sync` or `claude plugin update`.
- Compiled output (`plugins/mattstack/skills/`, `apps/board/skills/`) is written only by a compile or expand, never by hand.
- No em or en dashes in anything written. Stage named files only (`git add <path>...`).
- Plugin graphs use short ids and pass `check-dot.py --short-ids`; board graphs keep their sentence ids.
- Every skill edit loads mattstack:editing-skills, superpowers:writing-skills and mattstack:process-digraphs first.
- Write fence: `plugins/mattstack/attachments/review/`, `plugins/mattstack/attachments/review-posting/`, `plugins/mattstack/attachments/pipeline/` except `watch-ci/` and `stage-watch-ci/`, `apps/board/skills-src/`, generated `apps/board/skills/`, compiled `plugins/mattstack/skills/`, `plugins/mattstack/.claude-plugin/plugin.json`, `plugins/mattstack/pack/`, `plugins/mattstack/tests/` fixtures, `docs/superpowers/`, `.superpowers/`.
- Run only the test files touched; never the full suite.

## Review Focus

1. A GitHub PR-level comment (`gh-issue-comment-<n>`) or review summary (`gh-review-<n>`) reaching a reply or resolve: the reply posts through `mr_comment` with the quote and `@author`, and no resolve runs (Tasks 4 and 6 GREEN scenarios include one).
2. A resumed GitHub review whose inline comments landed but whose summary did not, or the reverse: `partly`, the refused-review gate, never a second submit (Task 3 GREEN).
3. A resumed respond pass where a PR-level reply already posted as a new PR comment: the posted read finds it among `gh-issue-comment` entries and does not post again (Tasks 4 and 6 GREEN).
4. A GitHub `mr_review_submit` returning `bad-anchors` that lists every comment (GitHub's 422): the bad-anchor move puts the listed findings in the summary and submits once more, inside the existing `bad-anchors` budget (Task 3 GREEN).
5. A GitHub ship where the domain wants squash: `mr_create` gets no `squash`, and `mr_update_squash` never runs on GitHub (Task 5 GREEN).
